# ADR-0002: Compatible gallery-dl Runtime for Delegated Playlists

- Status: Accepted by the user on 2026-10-26; implemented with scoped Builder validation recorded in the [handoff](../implementation/CACHE_LOCATION_BUILDER_STATUS.md). Independent review and complete acceptance remain outstanding.
- Date: 2026-10-26.
- Application source baseline: `047113c` (`2026.10.10`) plus the existing uncommitted cache-location implementation.
- Related decision: [ADR-0001](ADR-0001-unified-cache-location.md).
- Scope: CACHE-11 through CACHE-14 and backend acceptance cases AC-19 through AC-25.

## 1. Evidence and decision

The retained real-tool fixture used gallery-dl 1.32.18, yt-dlp 2026.10.21, synthetic extractors, and localhost media. The portable-mode HTTP and delegated single-video placement checks passed. The delegated playlist wrote `fixture.1.mp4.part` in the final destination despite an owned `part-directory`, and emitted aggregate `fixture.mp4` metadata. The failing parent stopped before temporary-mode execution. See `target/cache-location-supplement-real-gallery.log` and `target/cache-location-validation/real-gallery-27388-0/`. These are not standalone-EXE or real-site acceptance results.

The inspected [upstream playlist downloader](https://github.com/mikf/gallery-dl/blob/175d21fd8f7e52963911c02916d0634461cddb24/gallery_dl/downloader/ytdl.py) constructs an absolute indexed output under the final directory. A directory option in the Rust command cannot establish the required contract for that branch. Also, changing its staging path alone would not establish per-file finalization and accurate completion metadata.

Build gallery-dl as a separate compatible runtime from pinned source plus a small reviewed patch set. Keep the existing subprocess boundary and per-job storage policy. Correct playlist artifact finalization/events in that runtime, and verify its identity before any gallery operation. Managed installation/update must preserve that compatibility rather than overwrite it with the current official `latest` EXE.

This records the confirmed exception to the original no-new-dependency boundary. It does not authorize copying gallery-dl implementation into the MIT Rust application, adding Python as an end-user prerequisite, publishing a fork, changing the application version, or installing over the user's tools during development.

## 3. Playlist patch contract

Limit runtime behavior changes to delegated-playlist work paths, artifact finalization/metadata, compatibility reporting, and the hooks necessary for those operations. Planned patch points are `gallery_dl/downloader/ytdl.py`, the `DownloadJob` artifact completion boundary in `gallery_dl/job.py`, existing path helpers where required, and the project entry point. Reuse upstream extraction, format selection, retries, FFmpeg, and path sanitization. Do not patch every extractor or fork unrelated tool behavior.

### 3.1 Plan each artifact

After extraction without media transfer, enumerate the selected nonempty playlist leaves in existing order, including nested playlists. Preserve the upstream playlist-index/extension filename rule in the same final directory; do not rename ordinary single-video or HTTP outputs. Resolve each leaf's final path before downloading it and preserve literal-percent escaping, Unicode, postprocessing extension changes, and configured supported formats. Validate that final paths remain within the operation's requested output ownership and work paths remain within its unique part directory. Reject ambiguous colliding final paths before overwriting any output.

Carry an explicit per-artifact record containing original source metadata/archive key, leaf identity/index, planned final path, actual work path(s), final postprocessed path, and outcome. A group is not represented by a fictitious single file. The extension-aware final path must describe the actual resulting artifact, including merged/remuxed outputs. Do not infer it solely by replacing a string suffix.

### 3.2 Skip, download, and publish

Check the intended final artifact before media transfer using existing supported existence/skip semantics. An existing accepted artifact is kept byte-for-byte and produces a skip outcome without media transfer. Multiple artifacts sharing the original source archive key must not cause the first completed entry to suppress the remaining entries through the in-memory archive. Retain the native key; do not append an invented index or synthetic hash to it. Source/group archive completion is recorded only after all selected artifacts complete or are validly skipped.

Download new media, fragment/part files, merger inputs, and postprocessing work below `C/gallery-dl-temp/<job-id>`. Keep yt-dlp information caching at `C/yt-dlp`. Do not pass an absolute final output template to yt-dlp as its work output. After successful download/postprocessing, publish to the originally planned final path using existing safe path/move helpers. A same-volume rename is preferred. A cross-volume result is copied to a destination-local sibling publication file, closed/validated, then atomically published; that sibling is final-output transaction data, not a reusable cache. If publication fails, retain established outputs and report failure. Remove only this operation's incomplete publication file, and never overwrite a newly appeared conflicting final file silently. Destination-local publication preserves the tool's current timestamp/output semantics.

Each successfully published or already-existing artifact enters the existing metadata/XMP hooks exactly once, with its actual final path, original native source archive key, and source fields. Preserve the existing stdout JSONL schema and post marker. A post/group succeeds only when every selected nonempty leaf succeeded or was validly skipped. A failed child produces a nonzero operation outcome and must not emit a successful source-completion marker; already successful files/events remain valid. Cancellation stops later work, drains/closes subprocess/output consumers, and must not manufacture completion. No callback may advertise a nonexistent aggregate file.

Source-only/metadata-only analysis retains its existing preview meaning, download-disabled flags, and no-media-write contract. Its preview path is not a downloaded-file completion. The patch must not download media just to construct a preview or capability result.

## 4. Compatibility protocol and runtime lifetime

Add a side-effect-free entry-point option `--yt-dlp-gui-cache-capabilities`. It exits successfully with one JSON object containing `protocol: "yt-dlp-gui-cache-policy/v1"`, upstream version/commit, patch revision, embedded yt-dlp version, platform, and the features `owned-part-directory`, `playlist-artifact-finalization`, `actual-artifact-events`, and `metadata-no-media-write`. It does not contact a service, load personal Cookie data, create media/cache files, or start a gallery job.

A focused Rust `gallery_runtime_policy.rs` verifies the resolved runtime path and approved bundle inventory before executing that capability option. Check bounded protocol output and a bounded process timeout; unsupported/missing/mismatched values fail visibly. Do not execute an arbitrary candidate merely because it carries a convincing version string or sidecar. Development tests may inject approved fixture identities explicitly, but the production path must not have an environment-variable or settings bypass.

Acquire a shared `S/runtime/gallery-dl-runtime.lock` lease before inventory/preflight and retain it through command preparation, subprocess exit, output/XMP consumers, and work-directory release. Carry it with the existing prepared execution owner. All desktop/native-host/metadata entry points use this boundary. The normal storage-use lease remains separate and protects `C`. Managed replacement obtains this runtime lock exclusively before changing any installed bundle file and returns busy when acquisition fails, including cross-process use. Readiness/status probes are bounded and use the same compatible identity; do not equate presence with readiness.

Keep the existing configured gallery tool-path setting. A validated bundle at a custom path may be used without rewriting that setting; managed maintenance never replaces it. Missing, stock/unverified, modified, incomplete, or incompatible runtimes fail gallery preparation before media work, with an existing-tool-settings repair action. Normal yt-dlp operations, settings, and maintenance remain available. Runtime identity caching may avoid duplicate work only while the same verified files and operation lease remain in effect; replacement must invalidate it. Manual external tampering is not a supported hot-update mechanism.

## 5. Local bundle delivery and update policy

The first development implementation uses only an approved local bundle at `A/tool-bundles/gallery-dl/<bundle-id>/`, matched against the application lock. Validation artifacts are built below `target/gallery-dl-cache-policy/artifacts/` and copied into that input layout only inside controlled app fixtures. The managed destination remains `A/tools/gallery-dl`; executable-path settings and unrelated installed tools are not relocated. No production hosting URL, release asset, or publisher identity is fabricated.

Change the gallery-dl-specific install/update provider to consume that complete validated bundle. Disable the current Codeberg `latest` EXE and direct-asset fallback for this component, including first install, update, retry, and batch update paths. A missing/invalid approved bundle reports that the current runtime was kept; never silently install a stock incompatible EXE. A newer upstream version is not automatically compatible. Other tool providers and externally configured tool ownership remain unchanged. Future official builds may replace the patch only after equivalent verification and an explicit approved-lock update.

Use the following installation transaction; reuse existing atomic/state/lock helpers rather than create a general installer framework:

1. Resolve/validate the managed tool root, obtain the normal cache-use lease and exclusive gallery-runtime lease, and reconcile any prior `S/component-update/gallery-dl-install.yaml` journal. Never act on an external configured runtime.
2. Validate all input bundle paths/hashes/identity before modifying the installed tool. Copy/prepare source work under `C/temp/tool-install`; no unverified bundle is executed.
3. Prepare the complete destination-local sibling tree `A/tools/.gallery-dl-install-<transaction-id>` for publication. This is persistent installation transaction data, not disposable cache: journal its exact paths before preparation/publication, retain it across cache cleanup, and recover it before permitting gallery work. A valid old bundle inventory identifies its managed files. For a legacy managed install without that inventory, only `gallery-dl.exe` at the known default managed location is a replaceable legacy managed file. Preserve all other unrelated files at their relative paths; an unknown file colliding with a new managed path is an explicit conflict. Reject links rather than following them.
4. Journal the old/new inventory and recovery locations atomically. Retain the old tool tree under `S/component-update/gallery-dl-backup/<transaction-id>`, then publish the new directory. Windows multi-step directory replacement is not described as a single atomic exchange: the journal and exclusive lease prevent use of an intermediate state.
5. Verify the installed inventory and capability result, then write installed-version/build identity for the target installation. On error or interrupted startup, complete the validated transaction or restore the complete old bundle before allowing gallery use. Never claim success based only on EXE copying, and never leave an EXE with mismatched libraries.
6. Remove only verified transaction-owned obsolete publication/staging data. Preserve old bundle/recovery data until successful reconciliation; generic cache cleanup never deletes the recovery tree or journal. Unknown/external/user files are not cleanup targets.

If same-filesystem directory publication or rollback cannot be performed safely for the configured managed root, fail visibly before replacing it. Installation tests use fixture tool trees only. The user has not authorized replacing their actual configured runtime, system PATH tools, or any global package environment.

## 6. Source and notice delivery

Retain upstream gallery-dl copyright/license notices and its [GPLv2 LICENSE](https://github.com/mikf/gallery-dl/blob/175d21fd8f7e52963911c02916d0634461cddb24/LICENSE) with the derivative runtime/source. Inventory the embedded dependencies and retain their applicable notices; do not label the derivative as an official upstream binary or apply the application's MIT label to the dependency source. The Rust application remains a separate executable invoking the tool.

Any later distribution must include the corresponding source/build material and dependency notices as part of its reviewed delivery. This design specifies artifact completeness; it does not authorize distribution, a license change, upstream issue/PR messages, or a new release. No such external operation is required to prepare or test the local compatible runtime.

## 7. Alternatives and tradeoffs

- Keeping only `part-directory` failed in actual delegated-playlist execution and cannot close AC-19.
- Applying `-P temp` beside upstream absolute outputs does not establish staging placement.
- Staging every gallery output in Rust would also require taking over existing-file skips, output mapping, archive boundaries, and metadata behavior for ordinary HTTP/single-video downloads. This decision confines those changes to the failing playlist branch in the runtime that owns that behavior.
- Dropping playlist support or allowing it to bypass the selected cache policy would change the approved route-2 requirement.
- Waiting for an unverified future upstream fix supplies no currently testable completion path. A later verified upstream replacement can retire the bounded patch through the same identity/evidence gate.

The cost is a maintained, pinned derivative dependency, a standalone build/notice inventory, and a compatibility-specific update path. Older official gallery-dl installations will need a compatible bundle for gallery workflows. These user-visible changes were included in the user's confirmation of this amendment.
