## 2. Storage roots and compatibility

Let `A` be the stable application root provided by `runtime_paths::application_root()` and `T` the system temporary root captured once at startup. Release builds use the executable's containing folder; debug builds retain the existing project-root behavior. A change of working directory must not change storage roots.

| Saved mode | Active cache root `C` | Compatibility |
| --- | --- | --- |
| `v2_cache` | Resolve `storage.cache.dir` relative to `A`; empty means `A/cache` | Existing default and custom portable directories remain supported |
| `windows_temp` | `T/yt-dlp-gui/<installation-id>/cache` | Never use `T` itself as an application cache |
| `yt_dlp_default` | Normalize to `v2_cache` before runtime initialization | Read compatibility only; canonical save writes `v2_cache` and queues the frontend migration notice |

The installation ID is path-derived and stable across process restarts and executable updates within the same application folder. Use the first 32 lowercase hex characters of the existing SHA-256 implementation over the normalized canonical application-root representation. Normalize Windows separator, extended-path-prefix, and case differences before hashing; do not include PID, executable contents, timestamp, or the current working directory. A moved installation receives a new temporary namespace; its old temporary cache is retained. Portable paths continue to follow their existing relative/absolute configuration semantics.

Missing directories must remain configured and be created at initialization when valid. Remove the current cache normalization rule that resets a nonempty directory solely because it does not exist. Invalid paths, an unavailable temporary root, or write failures produce explicit errors; no fallback to another cache mode is allowed. Check roots and managed subdirectories against application/state/tool/output roots before accepting destructive ownership. Do not use a user profile, filesystem root, application root, or the unscoped system temporary root as `C`.

`S = A/state` is the persistent state root and is independent of cache location. Existing configuration, queue storage, managed executable locations, and completed download roots retain their current paths.

Preserve the existing lock and merge behavior that protects a newer background update history from a stale settings save. A legacy `manifest/state.yaml` still follows its existing import-to-config semantics, with source protection until import succeeds.

## 4. Shared path service and startup order

Add a focused `src/infrastructure/storage_paths.rs` path service. Keep `runtime_paths.rs` responsible for locating `A`; consumers must not repeat cache-mode branching or join `A/cache` themselves.

The service exposes these contracts (exact Rust field names may follow existing conventions):

- A pure resolver taking application root, captured system temporary root, normalized saved mode, and configured portable directory, returning validated resolved roots or a path error. Unit tests can inject roots without modifying global environment variables.
- An immutable `RuntimeStoragePaths` snapshot containing application root, installation ID, active mode, resolved cache root, persistent state root, and typed accessors for the layout in section 3.
- A process-wide initialization/access boundary, initialized once before cache/update consumers. No accessor reloads the configuration or silently initializes from a default on first use.
- Resolution of a saved next-start preference for UI display without initializing it, probing writability, creating its directories, or mutating the active snapshot.
- A storage availability/error state that prevents affected cache/update operations and destructive cleanup when initialization or migration is incomplete.

Normal GUI startup order is: establish `A`; acquire the storage-initialization guard; read and normalize saved settings; establish/protect/import persistent state; initialize the immutable active storage snapshot; then inspect/resume pending updates, register the process, restore caches/queues, launch background work, and schedule cleanup. Reorder the current pre-config pending-update check as necessary. Do not run startup cleanup before persistent-state migration/protection is established.

Every worker, cloned `ToolPaths`, downloader, thumbnail cache, and updater operation in a running GUI uses the same active snapshot. Saving configuration does not rebuild it. Companion processes launched for existing work receive explicit paths from that operation. An independently launched process reads its own startup snapshot; it must not overwrite another live process's snapshot or migrate state in use by that process. Native messaging operations that create application-owned cache/work files use the same service at their own startup boundary; browser-managed extension storage is unaffected.

The `--apply-update` runner is a special entry point: use the supplied manifest, target, staged, and backup paths. Derive application/state ownership from the target installation, not the runner executable's temporary folder. Do not load GUI settings or create another cache hierarchy beside the runner. Edition commands unrelated to cache operations retain their existing behavior.

## 5. Saving a next-start preference

Preserve `storage.cache.mode` and `storage.cache.dir`; `dir` is the portable directory preference even when temporary mode is selected. Keep the `windows_temp` token for on-disk compatibility while using a platform-neutral UI label.

For a user selection, clone the last successfully saved configuration, change only the candidate cache preference, and persist through the existing configuration lock and update-history merge. Publish the settings write atomically from a sibling temporary file so a failed write cannot leave a truncated settings document. Only publish the new in-memory saved preference after success. On failure retain the prior preference, active snapshot, worker state, and restart indicator, and return the error to the UI.

The running process's active cache mode/path must not be inferred from the mutable configuration after this point. Prepare diagnostics, summaries, cleanup, and operations started later in the same process still use active storage. The pending folder is informational until next startup.

For legacy `yt_dlp_default`, detect the original token before normalization, initialize the normalized portable policy, and retain a migration notice for this launch. Surface canonical-save failure; a later launch may show the notice again until canonical persistence succeeds. No automatic bulk cache migration accompanies this configuration conversion.

## 6. Persistent-state migration and old caches

Add focused migration logic in `src/infrastructure/storage_migration.rs`. This migration imports persistent state only; it is not a general cache transfer.

| Legacy source | Destination/action |
| --- | --- |
| `A/cache/manifest/{installed.yaml,installed_app_version.yaml}` | Same filename under `S/component-update` |
| `A/cache/manifest/pending_app_update.yaml` | `S/component-update/pending_app_update.yaml`, preserving transaction identity and absolute staged/target paths |
| `A/cache/manifest/backup` | `S/component-update/backup`, preserving all recovery files and reconciling pending-manifest backup references |
| `<configured-portable-cache>/state/music-cue-memory.yaml` | `S/music-cue-memory.yaml`; also inspect `A/cache/state/music-cue-memory.yaml` as the legacy default source when distinct |
| `A/cache/manifest/state.yaml` | Preserve the existing main-YAML history import; protect the source while an import is incomplete |
| `A/cache/temp/runtime/instances` | Inspect for live legacy instances before migration; new records use `S/runtime/instances`, without copying stale process records |

Migration rules:

1. Use an installation-scoped guard shared with the new updater/storage initialization path. Also inspect existing legacy instance and pending-update records. If another process or runner may own the data, defer migration and affected writes/cleanup with a visible busy error; do not relocate its live transaction.
2. Enumerate only the listed sources. Never scan a user's home directory or an entire system temporary tree for old state. For cue memory, prefer the saved configured portable source over the default source when both exist and no destination exists; keep the other source unchanged.
3. Copy into destination-local temporary files, validate the expected YAML schema or backup bytes, and atomically publish only when the destination is absent. A valid established destination is authoritative. Do not overwrite it from an older source. An unreadable/invalid destination or conflicting transaction requires an explicit error, not silent overwrite.
4. For backups, copy the referenced recovery files before publishing any pending manifest that refers to them. Preserve `staged_exe`/`target_exe`; rewrite `backup_exe` only after its destination is verified. Use a repeatable transaction/journal so an interrupted import can resume without losing the original recoverable combination.
5. Retain legacy source files and record completed imports in `S/storage-migration.yaml`. Do not reimport a completed source on every launch. Do not merge unrelated music-memory records or update transactions automatically.
6. Generic cache usage/cleanup excludes legacy `manifest`, `state`, and runtime coordination subtrees even after successful import. There is no automatic deletion of retained migration sources in this task. A deferred/failed migration blocks affected state writes and destructive cache cleanup; show enough path/operation context for recovery.

Do not automatically copy/move disposable audio, thumbnails, yt-dlp caches, or old work files when cache mode changes. Switching back reuses compatible entries through existing cache validation and expiry rules. Startup cleanup must not visit inactive roots just because they are known legacy locations.

## 7. yt-dlp output and external-tool boundary

Both supported modes explicitly supply `--cache-dir C/yt-dlp`. Application cache policy is authoritative over a loaded yt-dlp config's cache directory and temporary path; unrelated config settings retain their existing precedence. Preserve explicit cache disabling (`--no-cache-dir`) if already supported: disabled information caching must not cause writes at another location.

Use `C/yt-dlp-temp` for supported download intermediate files. Passing `-P temp:...` next to an absolute `--output` is insufficient: upstream documents that absolute output paths ignore `--paths`. For app-generated outputs, split the final destination directory from a relative output template, and pass the final directory through the appropriate home/output-path argument while retaining the cache temp path. Explicit absolute app requests must be represented equivalently without losing their final destination, filename, extension/template escaping, or final-path reporting.

For Issue #33 user-output operations, section 12.4 refines this layout: both downloader home/intermediate output are operation-private beneath the active `C`, and the application publishes completed artifacts to the selected final directory after processing. Ordinary output directories, chosen extensions and actual-result tracking remain supported; safe filename/collision policy supersedes direct publication to an occupied path. Internal audio/lyrics caches retain their explicit owned-cache paths.

Preserve final media and requested sidecars outside `C`. App-generated audio-cache/lyrics destinations beneath `C/audio` remain cache outputs, not completed user downloads. Format selection, postprocessing, retry, playlist-index, and final-output tracking contracts remain unchanged.

If an external yt-dlp config owns an absolute output template, normalize that supported case or reject the operation with a clear unsupported-output explanation before download; never claim the intermediate-directory policy is enforced when yt-dlp ignores it. Broader rewriting of arbitrary yt-dlp config syntax is outside this task. Upstream references: [filesystem options](https://github.com/yt-dlp/yt-dlp#filesystem-options) and [cache implementation](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/cache.py).

Audit application entry points that directly construct yt-dlp commands, including native-host operations, so covered information caches do not bypass the common policy. Do not promise control over unrelated internal caches created by third-party runtimes; document any concrete uncovered writer before proceeding with an implementation that would violate `CACHE-01`.

### 7.1 Native-browser cookie snapshot lifecycle

`browser_native_cookies.rs::NativeCookies::from_request`, reached through `browser_cookie_persistence.rs::incoming_records`, currently writes directly under `std::env::temp_dir()`. Replace only this temporary staging location; retain the existing validation, site scoping, persistent Cookie-store format, and source-selection behavior.

Acquire a shared storage-use lease before validating/creating the owned `C/temp/native-cookies` directory. Resolve it from the active snapshot; do not call `temp_dir()` again or derive it from the saved next-start preference. Use an unpredictable or process/time/counter-unique filename with exclusive creation; retry a collision without overwriting an existing file. Validate containment and reject link/reparse traversal using the common path boundary. Hold the lease in `NativeCookies` until all reads finish and its file has been closed and removal attempted. Close handles before removal on Windows. On partial-write/error paths, attempt removal before releasing the lease. Return an English operation/path error on creation or write failure; never fall back to the global temporary directory.

Successful release removes only that snapshot. Failed removal or abnormal termination may leave a disposable file: usage includes it, manual all-cache cleanup may remove it after exclusive ownership is obtained, and startup expiry removes stale entries older than the existing 24-hour transient threshold. Active snapshots must survive both cleanup paths. No cookie contents, Cookie values, or request serialization may enter logs, migration journals, or acceptance artifacts. Tests use synthetic credentials only. Do not scan, migrate, or delete legacy `yt-dlp-native-*.cookies` files in the shared system temporary directory.

### 7.2 Gallery-dl and delegated yt-dlp

Apply this policy to GUI and native-host downloads and metadata-only analysis through shared gallery-dl command preparation. Preserve `--config-ignore`, the in-memory archive, FFmpeg discovery, output events, XMP processing, and final destination planning. Cache options must be applied even when FFmpeg discovery fails; do not hide them behind the current FFmpeg-helper early return.

Supply `C/yt-dlp` as the delegated yt-dlp `cachedir` using gallery-dl's structured `raw-options` boundary wherever yt-dlp instances can be constructed (including its ytdl extractor when used). Preserve explicit cache disabling; it must not enable fallback caching. Encode paths as structured JSON/options rather than shell-concatenated text. Keep existing FFmpeg options when combining the cache policy. See upstream [yt-dlp construction](https://raw.githubusercontent.com/mikf/gallery-dl/master/gallery_dl/ytdl.py) for option merging; verify the supported installed tool version, not only upstream master.

For download work, allocate a unique owned `C/gallery-dl-temp/<job-id>` and configure gallery-dl's `part=true` and `part-directory` for each supported downloader, including HTTP and ytdl. Gallery-dl's [downloader base](https://raw.githubusercontent.com/mikf/gallery-dl/master/gallery_dl/downloader/common.py) supplies these controls. Its [ytdl downloader](https://raw.githubusercontent.com/mikf/gallery-dl/master/gallery_dl/downloader/ytdl.py) builds absolute media output templates, so adding yt-dlp `-P temp` alone is insufficient. The upstream playlist branch also differs from the single-video branch; do not assume that `part-directory` covers it. Actual delegated single-video and playlist execution must establish placement before acceptance. If a supported path cannot satisfy this policy while preserving output behavior, stop and return to design discussion rather than silently bypassing it or dropping playlist support.

Hold the shared lease before directory preparation until the subprocess has exited and all final-file moves, completion-event consumers, and XMP work using those files have finished. `PreparedGalleryDlDownload` or its execution owner must carry the work-directory/lease lifecycle so preparation, cancellation, errors, and early returns cannot release it prematurely. Keep separate jobs' work files isolated. Remove a completed/cancelled job's remaining owned work only after output processing; never delete user outputs. Failed removal or crash leftovers are counted in current-root usage, eligible for manual all-cache cleanup, and subject to the same 24-hour startup expiry as other transient work once exclusive cleanup ownership is available.

Metadata-only analysis keeps `download=false`, `directory-create=false`, `output.mode=false`, and `cookies-update=false`. Replace the nominal unscoped temporary destination with a path derived from the active owned gallery work namespace. It need not create a media work directory when no files are produced. Any delegated information-cache writes still use `C/yt-dlp` and hold the storage-use lease. No real-service or personal-account checks are required for automated fixtures.

Final filenames, gallery directory structure, XMP destination and archive keys, and existing-file skip handling retain their contracts. Section 7.3 corrects the inaccurate aggregate completion path for delegated playlists. Old `.part` files outside the active owned namespace remain untouched. No general gallery configuration file or fallback cache mode is added. The previous no-new-dependency restriction has only the compatible-runtime/build exception specified in ADR-0002.

### 7.3 Delegated-playlist correction and compatible runtime

The retained failure evidence is `target/cache-location-supplement-real-gallery.log` and `target/cache-location-validation/real-gallery-27388-0/gallery-playlist-observed.json`. With gallery-dl 1.32.18 and embedded yt-dlp 2026.10.21, the portable-mode HTTP and delegated single-video placement checks passed, but the delegated playlist created `final output .../playlist/storagefixture/fixture.1.mp4.part` outside its owned work directory. Its metadata event named aggregate `fixture.mp4` rather than the actual indexed artifact. This is controlled real-tool execution with synthetic extractors and localhost media, not a real-site or packaged-EXE result. The parent test stopped before temporary-mode execution. Do not change this historical failure into a pass or remove the case.

Use a separately built, source-pinned gallery-dl runtime with a bounded playlist-path/finalization patch, retaining the existing subprocess boundary. [ADR-0002](architecture-decisions/ADR-0002-gallery-dl-playlist-runtime.md) is normative for source identity, patch behavior, standalone build, capability protocol, local bundle install, update protection, and licensing/provenance artifacts. It replaces the assumption that `part-directory` alone is sufficient.

The patch plans each nonempty selected playlist entry's final path using the upstream indexed naming rule, stages its downloads and postprocessing beneath the operation's part directory, and finalizes each actual artifact to its planned destination before emitting a downloaded event. Existing final artifacts are checked before media transfer and produce skip events without modification. Original source-derived archive keys remain unchanged; never invent an aggregate successful artifact or a new key suffix. Each actual artifact receives one event and one existing XMP-processing opportunity. Source-level completion occurs only after the selected group finishes successfully or is validly skipped. Single-video and ordinary HTTP behavior remain covered by regression execution.

Require a verified compatible runtime before gallery analysis or download command preparation. Hold a shared installation-scoped gallery-runtime lease, as well as the storage-use lease, through subprocess and output processing. Managed installation/update requires the runtime lease exclusively and must not replace loaded executable/libraries. Do not auto-switch the configured tool path or run an arbitrary candidate merely to see whether it claims compatibility. Version strings and an editable sidecar alone are insufficient proof. Desktop, native messaging and metadata operations acquire this guard at actual use. Prepare/component status obtains the same verified result off the UI rendering path, as specified in 7.3.1; a stored display result cannot authorize execution.

Managed gallery-dl maintenance uses a validated local bundle whose identity is approved by the application lock. Suppress its old Codeberg `latest` EXE download/fallback paths for both install and update, including batch actions. Missing/invalid local bundles return actionable errors while retaining the old tool. Other managed components keep their current providers. Configured external tool directories are never overwritten. This development contract does not invent a production download URL or authorize publishing a fork.

## 8. Update, installer, and cleanup integration

Route installer and updater work-file helpers through the active snapshot. Persistent update metadata and backups use `S` even when `C` is temporary. Persist concrete artifact paths for a pending transaction; changing saved settings must not retarget that transaction to a different root.

On the next launch, inspect the stored pending manifest independently of the newly selected cache root. Validate its target and artifact ownership before acting. A pending transaction may still reference retained old cache artifacts; do not migrate or delete those artifacts merely because the active root changed. An update runner receives those exact validated paths. After applying an update, write installed-version state for the target installation and clean only that transaction's work files.

If the OS removes a staged executable or other required temporary update work, keep installed state and recovery backups intact, mark/report the pending transaction as failed, and allow a normal explicit retry/download. Do not replace the target executable, erase recovery state, or claim successful resume when a required artifact is missing.

All manual and startup cleanup must:

- Derive roots from active storage and retain existing age/expiry policies for their corresponding disposable subtrees.
- Count/remove only recognized disposable content, not the whole root indiscriminately. Retain unknown entries and legacy persistent-source subtrees. Include protected disposable update files in usage, but report them as kept during cleanup.
- Validate containment and reject symlink/junction/reparse-point traversal outside owned content, dangerous root aliases, state roots, and another temporary installation namespace. Do not recursively delete an arbitrary configured directory merely because it is named cache.
- Coordinate with active users of cache files, including downloads, playback, prefetch, thumbnail writes, cookie rescue, native-cookie snapshots, gallery-dl analysis/download/output handling, installation, and updates. Use a shared storage-use/cleanup boundary so checking busy state and starting deletion cannot race; destructive cleanup obtains exclusive ownership or returns busy. Honor same-installation process coordination and retain the existing conservative behavior when another instance may be using storage.
- Exclude artifacts referenced by an outstanding update transaction. Apply updater-specific recovery-backup retention only through its own lifecycle, outside generic cache cleanup.
- Return accurate removed/retained/error results. A cleanup that retained protected files must not claim the entire cache was removed.

If an active temporary root is removed externally, recreate the same root lazily for new work; report failures for in-flight work rather than switching modes or declaring success. This task does not repair arbitrary OS removal of files already open by a worker.

### 12.2 Template and filename planning

A focused `output_policy.rs` renders a **basename**, using the existing filename sanitizer and source identity helpers:

| Rule | Template |
| --- | --- |
| Title | `{title}` |
| Title + video ID | `{title} [{id}]` |
| Uploader + title + video ID | `{uploader} - {title} [{id}]` |
| Custom | Saved validated custom text |

Custom supports only `{title}`, `{id}`, `{uploader}`, `{upload_date}`; `{{` and `}}` represent literal braces. Date is `YYYYMMDD` when available. Missing title/uploader/date use `Untitled`, `Unknown uploader`, `Unknown date`. Missing ID uses `source-` plus the first 12 lowercase SHA-256 hex characters of the existing canonical source identity. ### 12.3 Reservation and collision behavior

Add a focused `output_transaction.rs`; avoid a general downloader/installer framework. Derive one intended **artifact group**: primary media plus its requested subtitle/thumbnail/metadata siblings, multiple section outputs where applicable, or one chapter-export directory. Sidecars use the same collision suffix as their primary media. An existing intended sidecar/directory also constitutes a collision, even if the primary media filename is absent.

Coordinate cooperating jobs through an application-marked `.yt-dlp-gui-output/` directory inside the validated final output directory, shared across installations. Its marker identifies the output-coordination schema/application, not one installation. Use OS-locked files keyed by normalized destination/stem identity, reusing existing file-lock/SHA helpers. Acquire the group reservation before media transfer and retain it through all output consumers/publication. Keep lock files stable; do not unlink/recreate a live coordination lock. Validate the marker; preserve unknown files or an unrelated same-named namespace and fail visibly rather than adopting/deleting them. This is final-output coordination metadata, excluded from cache usage/cleanup. It contains no Cookie values or full source credentials.

- **Keep both:** try the requested stem, then `stem (2)`, `stem (3)`, etc., treating an occupied file/directory or active reservation as unavailable. Reserve the whole planned group. Use the first free candidate. If a non-cooperating writer creates a conflicting artifact before any group artifact is published, choose another complete candidate and retry publication without overwriting the new file.
- **Skip:** when an intended existing artifact is found, return `SkippedExisting` with that concrete path and do not start media transfer or postprocessing. If only a live reservation exists, wait cancellably, then recheck: skip if its completed file exists or claim the now-free target if the other job failed without publishing.
- **Late multi-artifact conflict:** publication is atomic per file, not for an arbitrary set of sibling files. If some complete artifacts were already published before a new conflict/error, preserve them and all conflicting existing files, report partial failure and list published paths. Do not delete published files as rollback or report the entire group complete. Before first publication, precheck the entire actual artifact manifest under the reservation to minimize this case.

A successful `exists()` preflight is never authority to replace a file later. The final non-replacing filesystem operation is authoritative even for processes which do not honor these locks, alternate Windows aliases, and different installations. Unsupported locking/publication primitives fail safely with a destination-specific error; there is no overwrite fallback.

### 12.4 Staging, processing and final publication

The operation owner acquires a #32 storage-use lease before creating work or preparing a command. Allocate a unique checked directory beneath `C/yt-dlp-temp/<operation-id>/` for direct downloads/online audio and their sidecars; use `C/transcode-temp/<operation-id>/` for cached-copy/conversion work when appropriate. Exclusive creation prevents sharing another job's files. Both directories remain within existing disposable parents. Hold ownership in the prepared execution object and move/clone the necessary owner into every producing/consuming thread before spawning; a plain Command must not outlive its transaction/cache guard.

Set yt-dlp home/output and temp paths to private work, including supported explicit absolute app requests. Configure every generated media/sidecar/chapter template to stay there. Downloader overwrite flags and FFmpeg `-y` may target only this operation's verified private work. Cached copies also write a staged artifact. A pending automatic transcode carries the same owner across workflow handoff; download completion must not release ownership or advertise a final user file prematurely. Source user media supplied for conversion remains intact when another final path is produced; this feature does not authorize replacing that input.

After producer exit, pipe/thread teardown and all postprocessing:

1. Collect the actual completed artifact manifest from known tool events and the private work tree. Validate paths/regular files and reconcile actual extensions/section paths with the final group before writing outside `C`. Unexpected or escaping tool outputs fail; metadata-only cache/analysis output is not a final artifact.
2. Apply requested final metadata/timestamps to owned staged artifacts. Reserve/recheck the final group as above.
3. Move each complete artifact with a non-replacing atomic primitive. On Windows reuse the `MoveFileExW` pattern with replacement disabled. 4. Such a sibling is an owned final-publication transaction, not a download fragment/cache fallback.
5. Return the actual final path(s). Remove only this operation's unpublished private work/siblings after producers settle, then release reservations and cache ownership. Preserve complete already-published artifacts on later failures.

Do not remove an existing target before a move, copy directly over it, run FFmpeg against it, or remove an original user file to make a conflicting destination available. Existing overwrite-first subtitle/transcode finalizers and `unique_music_output_path` existence checks must be replaced/integrated at user-output boundaries. Scope: clean cancellation and handled I/O/tool failures, concurrent/racing final writers, and restart preservation of completed files. Abrupt termination may leave owned destination-local publication siblings; do not reuse or auto-delete them merely because their filename resembles this operation's prefix. General power-loss resume/orphan recovery and transactional rollback of multiple already-visible files are not added. Unknown/pre-existing files remain protected.
