## R-OUT-001: Reserve intended outputs rather than treating the conversion input as a collision

- Locations: `src/infrastructure/output_transaction.rs:167-183` (`collision`), `198-256` (`reserve`); `src/app/post_process_worker.rs:413-431` (standalone conversion reservation and early skip).
- Contract: OUTPUT-02/06; backend 12.3/12.4 and OUT-AC-02/06. Skip concerns an intended output artifact, while original conversion inputs must remain intact.
- Trigger: choose Skip existing files and request standalone conversion of an existing `Clip.mp4` to `Clip.mkv` in the same directory, with no `Clip.mkv` or requested output sidecar present.
- Actual behavior: the transaction receives only the input's directory and stem. `collision` accepts every entry equal to the stem or beginning with `stem.`. It therefore selects `Clip.mp4`, and the worker returns `SkippedExisting` before staging or running FFmpeg. Standalone conversion under Skip cannot produce the absent output in this ordinary case. Keep both also adds an unnecessary suffix. The same broad predicate treats unrelated same-stem extensions as collisions in other export routes.
- Expected behavior: distinguish the source input from the actual intended final artifact group. Convert to an absent requested output while preserving the source; skip when an intended output/sidecar is occupied. Preserve non-replacing commits and group protection.
- User impact: selecting Skip silently prevents requested conversions whose output does not exist, and names are changed for unrelated same-stem neighbors.
- Cause: the reservation API has no intended extension/artifact information, and stem-prefix enumeration substitutes for planning the group.
- Evidence boundary: retained Builder fixtures contain `source.mp4` and `source (2).mkv` under both `target/output-validation/actual-39720-1793093229927/{portable,temporary}/`, consistent with the Keep both branch. The standalone test at `src/app/state/output_review_tests.rs:620-650` uses default Keep both and checks only existence/input preservation; it does not exercise Skip with an absent conversion output. Reviewer did not run this scenario.
- Repair acceptance: in both cache modes, exercise the real standalone worker with Skip, existing source and absent different-extension target; assert a published target with correct extension and unchanged source hash. Then occupy the actual target/requested sidecar and assert explicit skip plus unchanged hashes. Include an unrelated same-stem file and retain existing late-race, partial-publication and grouped-sidecar protections.

## R-OUT-002: Do not freeze a queue display placeholder as the automatic title

- Locations: `src/app/state/queue_batch_helpers.rs:37-42`; `src/app/state/queue_worker_actions.rs:68-76`; `src/infrastructure/output_preparation.rs:23-32`, `62-64`.

- Contract: OUTPUT-03/05; backend 12.1/12.2 and OUT-AC-03/05. Automatic Title means source title, and naming metadata is resolved before the final plan is frozen.
- Trigger: dispatch a freshly populated, unanalysed URL-only batch item using the default Title naming mode, without an external output template. Its display title is `Imported {URL tail}`.
- Actual behavior: `output_request_for_item` places the nonempty display placeholder into `context.title`. The later `--print-json`/metadata event cannot correct the already frozen transaction. A URL such as `.../watch?v=abc` thus produces a sanitized `Imported watch...` name rather than the extractor's title.
- Expected behavior: distinguish a display/inferred title from resolved naming metadata and obtain the requested item's actual metadata before reserving an automatic title. Freeze that resolved plan for retries. Use the documented fallback only when the extractor actually lacks the field; preserve playlist-item identity when resolving metadata.
- User impact: the default, common batch workflow saves misleading URL-derived names even though the tool can supply the real title.
- Cause: nonempty text is used as evidence that naming metadata has already been resolved; the request carries no equivalent completeness distinction.
- Evidence boundary: real-tool requests in `output_review_tests.rs` supply their title context explicitly, and the GUI fixture seeds ready metadata. Their successful filenames do not cover the URL-only application dispatch. No Reviewer network or tool run was performed.
- Repair acceptance: pass an unanalysed item through the real `start_download_task_at` route using controlled metadata whose title differs from the display placeholder. Verify actual Title output in both modes, explicit fallback when metadata genuinely lacks title, and stable final naming across retry/settings changes. Retain the no-network settings-preview rule.

## R-OUT-011: Stop cannot interrupt pipe draining after the tracked parent exits

- **Severity/status:** Medium / P2, Open.
- **Locations:** `src/infrastructure/process_guard.rs:90-161`, `192-203`; `src/app/media_probe.rs:53-81`; `src/infrastructure/tools.rs:291-298`, `1331-1354`; `src/app/state/music_worker_helpers.rs:418-420`, `518-520`, `612-614`; `src/app/post_process_worker.rs:910-921`; `src/app/state/workflow_download_actions.rs:344-385`.
- **Trigger:** An operation-owned executable or launcher starts a descendant that inherits stdout and/or stderr, then the tracked parent exits or fails while that descendant is still alive and keeps the pipe open. The reader thread is draining that pipe; the user requests Stop after the parent has been observed as exited. This can affect a supported configured tool/launcher or an external-tool failure; it does not require abrupt application termination.
- **Actual behavior:** `run_tracked_command_output_cancellable` polls the flag only until `child.try_wait()` reports the tracked parent exited. It then synchronously joins the `read_to_end` threads before checking the flag again. A descendant holding an inherited write handle prevents EOF, so the join can remain blocked while the cancellation flag is no longer polled. These probe/postpass children are owned locally by the helper rather than the workflow's `download_child` handle, so the normal Stop handler cannot reach the remaining producer through that handle. The operation and cache/output ownership can remain busy until the descendant finally closes the pipe; the same wait can delay an error result even before Stop.
- **Expected behavior:** Retain a cancellable means of settling the entire operation-owned producer tree and both readers through pipe drain, including when the initial tracked parent exits first. Stop should return a cancelled result and release ownership only after the remaining producer/readers have settled; ordinary successful output should still be fully drained.
- **Impact/cause:** A stopped download/conversion can remain stuck in stopping and block cache cleanup for as long as an orphaned descendant holds a pipe. Existing final outputs remain protected by the publication boundary. The helper changes from cancellation polling to blocking `join` as soon as the direct parent exits, without a remaining cancellable tree/reader owner.
- **Evidence classification:** Static analysis of the common helper and actual caller/Stop paths; no Reviewer process was started or terminated. Builder's new fixture at `src/app/state/output_probe_fixture.rs:61-76` keeps the tracked parent alive while its child holds the pipes, so its passing cancellation cases do not cover the parent-exited-first trigger. This is a distinct boundary from the active-parent R-OUT-010 repair.
- **Repair acceptance:** In both cache modes, use a project-local controlled producer/launcher through an actual affected workflow. Start a descendant that inherits and holds both pipes, record that the tracked parent has exited while the descendant remains alive, then request Stop. Assert prompt cancellation, descendant and both readers settled, no later producer or final publication, unchanged existing inputs/outputs, and eventual exclusive cleanup. Include a tool-failure/early-parent-exit case and a successful naturally drained case, and retain the active-parent ffprobe/encoder/postpass cancellation controls. Do not treat an injected early-exit case as a live-service or arbitrary-power-loss test.

### R-OUT-020: rejected music configuration leaves a running processing-log action

- **Severity/status:** Low / P3, Open. **Evidence:** static source/caller analysis, supported by Builder's recorded rejection test; Reviewer did not run the application or reproduce this in the GUI.
- **Locations:** `src/app/state/music_metadata_helpers.rs:167-180`, `src/app/state/music_prefetch_actions.rs:39-62,178-204`, `src/app/state/music_event_actions.rs:21-37,92-111,182-214`, `src/app/state/log_actions.rs:32-46,162-169`, `src/app/state/log.rs:60-69`, and `src/app/state/output_review_metadata_tests.rs:321-335`.
- **Trigger:** A playback or prefetch resolve selects an unreadable, malformed or unsupported yt-dlp config, such as a config containing the intentionally forbidden `--exec`. The failure occurs before an external tool attempt. It does not require concurrency or a config change during the operation.
- **Actual behavior:** Each caller creates a processing-log action with `Running` before invoking the resolver. The new outer bind returns `Err` with an empty `attempts` vector. Therefore neither worker emits a `ToolCommandFinished` event. The separate `Resolve` event handles the playback error or clears prefetch pending state, but does not carry or settle that log action. Its empty step list remains `Running`, displayed as an ellipsis. For playback, the error is still reported in the item/player state; this finding does not claim playback itself stays active. Prefetch retains its existing skipped/error handling but likewise leaves its log row running. The log trimming code excludes `Running` actions, so these orphaned rows are also not eligible for normal trimming.
- **Expected / user impact:** A completed configuration rejection must settle the processing-log action according to the existing playback failure or prefetch-skip behavior while accurately indicating that configuration preparation failed before a subprocess was launched. A user inspecting the log should not see a finished operation as still running. The existing configuration error and no-launch/no-retry behavior must remain intact.
- **Cause:** The repair moved configuration binding before the attempt bookkeeping, but the callers' log completion is driven exclusively by the returned attempt records. Before this change, an analysis error produced a failed attempt record; the new early return bypasses that completion path. Builder's helper-level test explicitly expects zero attempts, but does not check the enclosing playback/prefetch action state.
- **Repair acceptance:** Exercise both actual playback-resolve and prefetch-resolve event paths with a rejected config. Verify that their processing-log actions reach the appropriate terminal state, the failure is represented without claiming a tool was launched, playback still exposes the error, prefetch pending state is cleared, and there are no tool attempts or cookie-free retries. Retain the one-read/interpretation/validation and successful/retry metadata cases. Use the existing state/event flow; no speculative concurrency protection or additional general framework is requested.
