## 1. Scope and approval

This document specifies the Issue [#32](https://github.com/kannagi0303/yt-dlp-gui-v2/issues/32) cache-location change and Issue [#33](https://github.com/kannagi0303/yt-dlp-gui-v2/issues/33) output protection/naming change for yt-dlp-gui v2. Its filename follows this workspace's `AGENTS.md`; it does not describe the EROffice product.

Issue #32 passed Reviewer Round 3 for source and supplied controlled validation, with R-CACHE-001 through R-CACHE-005 and V-CACHE-001 closed in the [review report](docs/reviews/REVIEW_CACHE_LOCATION_ISSUES.md). Its implementation remains uncommitted against baseline `047113c` (`2026.10.10`). The historical unmodified gallery-dl failure and evidence qualifications remain in the [Builder handoff](docs/implementation/CACHE_LOCATION_BUILDER_STATUS.md). Package/release acceptance is separate.

The user confirmed the Issue #33 proposal and detailed architecture: default keep-both collision handling, an optional skip policy, naming presets and a controlled custom template with preview, shared final-output protection, and combined submission with #32 after validation/review. Sections 6/7 are implemented with Builder validation documented in the [Issue #33 handoff](docs/implementation/ISSUE_33_BUILDER_HANDOFF.md). Independent review of the combined change remains pending. The prior #32 pass does not cover #33.

New documentation, identifiers, comments, diagnostics, and canonical UI copy for this task use English. Existing user locale preferences remain supported through the project's i18n system. Agent conversation with the user remains in Chinese.

## 2. Product requirements

| ID | Requirement |
| --- | --- |
| CACHE-01 | A cache-location choice controls all application-owned, reproducible disk caches and work files listed in the backend reference, including audio, artwork, lyrics, queue thumbnails, yt-dlp information caches (direct and gallery-dl-delegated), gallery-dl/download/transcode work files, temporary native-browser cookie snapshots and cookie-rescue profiles, and component-update download/staging work files. |
| CACHE-02 | Offer two choices: **Application folder (portable)** and **System temporary folder**. Portable is the default. Preserve the existing configured portable `storage.cache.dir`, whose default is `<application-root>/cache`. System temporary storage uses `<system-temp>/yt-dlp-gui/<installation-id>/cache`. |
| CACHE-03 | Keep existing serialized values `v2_cache` and `windows_temp`. Accept legacy `yt_dlp_default`, map it to portable, save the canonical value, and show a migration notice. Do not offer the legacy choice for new selections. |
| CACHE-04 | Save location changes for the next application start. Every operation in an already running process continues to use its immutable active location, including operations started after the preference is saved. Display the active folder and any different saved folder separately. |
| CACHE-05 | A failed settings save does not change the saved selection shown in the UI or the active storage policy. Display an actionable English diagnostic. Do not claim that a failed save succeeded. |
| CACHE-06 | Changing locations does not automatically move, copy, or delete reproducible caches. The previous cache remains available when its location is selected again. Usage and cleanup refer only to the active cache. |
| CACHE-07 | Persistent application state, installed-version records, pending-update records, update recovery backups, and music cue memory live beneath `<application-root>/state`. They do not follow cache location and are excluded from cache cleanup. Existing configuration, queues, tools, and completed download locations retain their existing ownership. |
| CACHE-08 | Safely import existing persistent state from its legacy cache paths before permitting destructive cache cleanup. Migration is repeatable, does not overwrite established destination state, retains legacy sources, and reports failures. A legacy source retained for migration is not an ordinary disposable cache entry. |
| CACHE-09 | An invalid or unwritable selected location produces a visible storage error; it must not silently redirect writes to another location. A configured directory that does not exist yet is valid if it can be created. System temporary storage may be removed by the OS and is recreated when safe to do so. |
| CACHE-10 | Cleanup operates only on validated, application-owned cache content. It must not clear the system temporary root, another installation's temporary namespace, persistent state, unrecognized files, or files outside the selected root through links. Active work and pending update artifacts must be protected. |
| CACHE-11 | Cached yt-dlp information and supported intermediate download files must actually land beneath the active cache root. Preserve existing output locations, extension/container choices, sidecars and actual-path reporting. Issue #33 may change an automatically generated basename when the user selects a naming rule, or append a collision suffix under OUTPUT-01; its safe publication contract supersedes unconditional reuse of an occupied filename. An absolute output request must not silently bypass the intermediate-directory policy. |
| CACHE-12 | Validate actual filesystem behavior for both locations, restart boundaries, compatibility, failures, cleanup, and updater continuity. Command-argument inspection alone is insufficient evidence for storage correctness. |
| CACHE-13 | Use a traceable, compatibility-verified gallery-dl runtime that enforces the cache policy for delegated playlists. Retain the existing tool-path setting and final filename planning. Each downloaded/skipped playlist artifact must report its actual final path and original source-derived archive key; a nonexistent aggregate file must not be reported as completed. |
| CACHE-14 | A gallery-dl runtime installation/update must preserve this compatibility requirement. An unverified official `latest` executable must not replace the compatible runtime. Missing/incompatible runtimes produce actionable feedback before gallery work starts, while settings and unrelated download backends remain available. The local build, provenance, installation, and update boundaries are specified by ADR-0002. |

## 3. User workflow

1. Open **Options > Cache** and see the current cache folder and usage.
2. Choose one of the two supported locations. A successful save displays **Restart required** and the folder to be used after restart. Existing and newly started work in this process stays on the current folder.
3. Restart the application normally. The saved location becomes active, all covered cache consumers use it, and the pending-change notice disappears.
4. Use refresh or cleanup against the current location. Previous caches are retained and excluded from current usage. Cleanup reports busy or protected content without deleting active files.
5. Select the previous location and restart to reuse any compatible cache content that still exists there. System temporary cache contents are not guaranteed to survive OS cleanup.

If storage initialization or migration fails, show the failing operation and path, allow the user to save a corrected next-start preference, and disable affected cache/update operations and destructive cleanup. Do not continue those operations with a mixed or implicit fallback layout.

Gallery operations additionally verify the configured runtime. If it is incompatible, use the existing dependency/tool settings to select or install an approved compatible runtime; changing the cache selector alone does not repair a tool compatibility failure. The managed gallery-dl installer/update action uses a validated local bundle in this development stage. It does not download an unverified upstream `latest` replacement. No compatible production download endpoint is assumed to exist.

Gallery status re-review amendment, proposal and structural detail confirmed before follow-up implementation: startup, tool-path changes and managed-maintenance completion refresh compatibility in the background. A completed check updates an idle interface without requiring another user action. While Checking, About disables gallery Install and Main shows checking guidance; installation/update is not queued from this pending state. After the actual result arrives, retain the existing Ready/Missing/Incompatible/Busy behavior and configured-external-tool ownership. This adds no setting or automatic runtime replacement. Backend 7.3.1, frontend 5.1.1 and ADR-0002 4.1 define implementation and controlled acceptance.

## 4. Boundaries

Here `A` is the application root, `C` is the active cache root, and `S` is the persistent state root, as defined in backend section 2.

- This change does not add a general cache-folder picker, cache transfer wizard, automatic old-cache deletion, or live directory switching.
- The existing advanced portable directory configuration remains supported; a missing directory is not reset merely because it does not exist.
- Final user downloads are output data rather than cache. Browser-managed extension storage, browser profiles owned by the user, and unrelated external-tool/OS caches are outside this ownership contract. Application-created cookie-rescue profiles and native-browser cookie snapshots are in scope. Persistent managed credentials remain at their existing `A/data/cookies` location and must survive cache cleanup; this task does not relocate them to `C` or `S`.
- Native-browser snapshots use `C/temp/native-cookies`; gallery-dl intermediate files use `C/gallery-dl-temp`, and its delegated yt-dlp information cache uses `C/yt-dlp`. These writers follow the same startup snapshot and cleanup coordination as other covered consumers. Legacy snapshots directly under the system temporary root and old gallery work outside `C` are not searched, imported, or deleted.
- Gallery final media, XMP placement, archive-key values, and existing-file skip decisions retain their contracts. The playlist amendment corrects completion reporting where the previous tool emitted an aggregate path that did not exist: emit actual artifact paths instead, without inventing archive-key suffixes. Metadata-only analysis must not write nominal output files to the system temporary root. No separate cache setting is added.
- The previous no-new-dependency boundary has one confirmed exception: a source-pinned, locally patched gallery-dl runtime and its standalone build inputs under ADR-0002. No new Rust runtime dependency or external Python installation for end users is part of the confirmed design. Existing configured external tool paths are not rewritten or overwritten automatically.
- Download/intermediate media remains below `C`. Short-lived destination-local files needed to atomically publish a final output, configuration, or installed tool are owned publication transactions, not reusable cache; the corresponding output/install transaction must recover or remove only its own files. This exception does not permit `.part` downloads beside final media.
- A cache location change does not change the selected UI language, relocate installed tools, or change update/release authorization.
- Package builds, installation, version changes, commits, publishing, and release operations are not authorized by document approval.

## 6. Issue #33 product requirements

| ID | Requirement |
| --- | --- |
| OUTPUT-01 | Default to **Keep both files**. An occupied target produces a new common basename, starting with `Title (2)`, for this operation's media and sidecars. Preserve every established conflicting file. Repeated downloads and different sources with identical titles follow the same rule; matching a filename does not establish matching content/source identity. |
| OUTPUT-02 | Offer **Skip existing files** as the alternative. If an intended artifact or chapter destination is occupied, skip the operation with an explicit existing-path outcome. Do not transfer media, modify existing media/metadata/sidecars/timestamps, or claim a newly downloaded artifact. A live reservation is busy work, not proof of an existing completed download. |
| OUTPUT-03 | Offer **Title**, **Title + video ID**, **Uploader + title + video ID**, and **Custom template**. Keep Title as the default for compatibility. User-selected presets affect automatic naming; explicit per-item/Save As names retain priority and still receive collision protection. |
| OUTPUT-04 | The custom basename template supports `{title}`, `{id}`, `{uploader}`, `{upload_date}`, literal text and escaped braces, with filename preview and validation. It does not select a directory or extension. Unsupported expressions, empty/invalid templates and unsafe literal path syntax fail visibly before a save/download. Missing metadata has deterministic safe fallbacks. |
| OUTPUT-05 | Persist output preferences atomically. Failed saves retain the last saved preference and queued/running request behavior. Successful changes apply to newly dispatched automatic output jobs without restarting; each running operation keeps its captured settings. Existing explicit and legacy saved filenames remain literal. Preserve unrelated configuration/history and the user's locale. |
| OUTPUT-06 | Direct yt-dlp, desktop/native requests, online/cached audio exports, chapter exports, standalone subtitles, sidecars, remuxing and built-in transcode finalization use the same protection. Protection includes final moves, copies and postprocessing, not just yt-dlp flags. Existing advanced configuration cannot enable silent final-file replacement. |
| OUTPUT-07 | Coordinate same-output operations across threads, processes and installations, including Windows alias spellings. Use collision-resistant private staging and non-replacing final publication. A destination created after preflight must also survive. Never rely solely on `exists()` followed by an overwriting operation. |
| OUTPUT-08 | On cancellation or publication/postprocess failure, stop/settle the producers and clean only this operation's unpublished work, subject to the ordinary-Stop boundary below. Established files and already published complete artifacts survive. Report partial publication accurately. Keep cache-use ownership through the complete processing/publication lifetime. |
| OUTPUT-09 | Downloads, fragments, conversion and sidecar work remain under the immutable active cache root from #32. Destination-local publication siblings contain only closed, completed artifacts being committed; cache cleanup never owns final downloads or shared destination coordination files. Preserve restart/pending-cache and safe-path behavior. |
| OUTPUT-10 | Preserve the approved gallery-dl runtime, source-derived filenames, archive keys, existing-file skip semantics and XMP behavior under ADR-0002. The new naming/collision selector governs direct yt-dlp/audio output jobs, including native requests using that backend. It does not silently rename gallery sources or replace their established policy. |
| OUTPUT-11 | Verify same-title/different-source and repeated-source jobs, existing media and sidecars, concurrent/racing writers, skip, cancellation, failures, naming persistence/preview, and actual result paths in both cache modes. Hash existing user fixtures before and after. Include current-source GUI evidence and combined #32 regressions before submitting both issues. |

## 7. Issue #33 workflow and limits

Ordinary-Stop boundary, selected by the user on 2026-10-28 for R-OUT-015: stop an active tracked tool using the existing process-cleanup mechanism, prevent later processing/publication, and retain ownership until its process/output consumers settle. If the tracked parent has already exited but a descendant still holds stdout or stderr, Stop may wait until that descendant naturally finishes and both pipes reach EOF. The same draining delay may affect a parent-failure result. During that wait, retain output/cache ownership and keep cleanup busy; do not report settled cancellation or completion prematurely. Prompt termination of that exited-parent descendant is not a product guarantee. No occurrence frequency or fixed maximum wait is asserted. The user confirmed this structural boundary on 2026-10-28; implementation and executed acceptance remain recorded separately.

Open **Options > Download output**, select the naming and existing-file policies, and optionally edit/preview the custom template. Save a complete valid candidate. A new automatic job captures that saved policy; an existing explicit filename is honored as its requested basename. At a collision, keep both with a suffix or return an explicit skip according to the captured policy. Show the actual published path and any renaming/skip/partial result. An OS Save As dialog's existing-file confirmation does not authorize the application's download pipeline to overwrite a file.

External configuration boundary, confirmed as a repair proposal on 2026-10-28 for R-OUT-012: each new logical operation resolves/parses its supported yt-dlp configuration once and reuses that typed result for application planning and command-option ownership. The external tool still reads the original selected file itself; application parsing does not make the file immutable. Finish or stop the running operation and wait for ownership release before editing/replacing its configuration, then start a new operation. Consistency during concurrent external configuration edits is not guaranteed. No watcher, automatic config hot reload, private config copy or user-file rewrite is added. The structural detail in backend 12.5.1 and ADR-0003 section 7 was confirmed by the user before implementation.

R-OUT-012 re-review amendment (proposal and structural detail confirmed before follow-up implementation): a playback/prefetch cache operation shares its captured configuration between primary and cookie-free retry preparation. Supported option values remain values even when they resemble format or output-path switches; they do not silently change the selected format or save folder. Main's output selector and path display share one observation during a render, with fresh observation on the next render. Preserve existing supported configuration behavior and the original-file consistency limitation above. The user confirmed the detailed design/validation in backend 12.5.1, frontend 8.2 and ADR-0003 section 7 before this follow-up implementation.

Protected-configuration follow-up (R-OUT-016 through R-OUT-019): the user confirmed the repair proposal on 2026-10-28; the user confirmed this structural amendment on 2026-10-29 before implementation. An optional leading UTF-8 BOM is supported without changing the file. A standalone config `--` is unsupported because it can disable the application's later cache/output and analysis options; report the terminator and ask the user to remove it. The supported built-in `-t` / `--preset-alias` preset is `sleep`. Output-affecting `mp3`, `aac`, `mp4` and `mkv`, and unknown presets, fail with the supplied option/value and a repair explanation; select the relevant app audio/conversion operation or use individual options supported by protected output. The app does not silently rewrite the user's config.

Analyze, source discovery and automatic naming preflight remain metadata-only even when the config requests `--no-simulate` or `--force-overwrites`. They use the same protected configuration boundary as output planning; an unsupported hook or config destination fails before execution. An analysis action must not download media, write sidecars or overwrite an existing output. After metadata resolution, an authorized actual download may retain those supported flags and relative naming intent only under the existing reserved private-work and keep-both/skip publication policy. Backend 12.5.4 and ADR-0003 section 8 define the shared boundary and real-tool acceptance in both cache modes with explicit/portable configs, transfer counts and preserved established-file hashes. The one-operation config reuse and original-file consistency limitation above remain in force.

The template is a filename feature; output-folder selection and the #32 cache/output separation remain authoritative. No overwrite mode, new arbitrary scripting language, general downloader framework, download archive migration, or retrospective renaming of completed files is added. Metadata/tag writes associated with this new download operate on its staged artifacts; separate intentional edits to an already owned file are not a new same-name download.

The backend section 12 and acceptance cases `OUT-AC-01` through `OUT-AC-14`, frontend section 8 and ADR-0003 define implementation boundaries. New Rust runtime dependencies and a gallery bundle rebuild are not planned. The combined commit requested by the user is deferred until the combined change has completed its required review gates. Push, PR, merge, version/package and release operations retain their separate authorization boundaries. The existing ignored `/docs/` policy is unchanged.
